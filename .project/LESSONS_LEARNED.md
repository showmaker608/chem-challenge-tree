# 化学知识挑战树：长期复盘与项目红线

> 更新日期：2026-08-27  
> 用途：记录这个项目长期迭代中反复出现、最容易误判、以后必须优先检查的问题。它不是功能清单，也不替代每次发布前的实际验证。

## 一句话结论

这个项目现在最缺的已经不是“再多做几个功能”，而是把三件事真正闭环：**先保护学生数据，再验证学生是否真的学会，最后才扩大传播和商业化。**

项目中最危险的误判不是代码写错，而是把下面这些状态混在一起：

> 本地做出来了 ≠ 本地验证通过 ≠ 已部署 ≠ 已发布 ≠ 有真实学生使用 ≠ 教师认可 ≠ 学习有效 ≠ 有人愿意付费

没有证据时统一写 **“尚未采集”**，不能写成 0，也不能用别的数字替代。

## 0. 当前最紧急的问题：学生数据安全门槛还没有闭环

### 已确认的线上状态

2026-08-27 复核线上 `manageCodes`：

- 匿名请求 `listStudents`：HTTP 200，返回 28 条；
- 匿名请求 `listFeedbacks`：HTTP 200，返回 2 条；
- 本地 `manageCodes` 已有教师令牌鉴权和字段白名单补丁，但这不能证明线上已经生效。

因此，在以下条件全部满足前，不能写“风险已修复”，也不应继续把新学生引导到真实账号注册：

1. 完成 CloudBase 登录；
2. 部署 `manageCodes` 云函数；
3. 线上匿名请求 `listStudents` 返回 HTTP 403；
4. 线上匿名请求 `listFeedbacks` 返回 HTTP 403；
5. 使用有效教师令牌仍能正常读取必要字段；
6. 确认响应中不再出现密码、PIN、令牌哈希等私有字段。

### 仍需专项修复的源码级安全债务

以下是当前源码中可以观察到的风险，不等于已经发生了数据破坏，但必须按高优先级处理：

- `studentLogin` 仍以明文保存和查询密码；需要设计兼容旧账号的哈希迁移方案，不能直接切换导致所有学生无法登录。
- `updateProfile` 只凭班级码和学号即可更新昵称、头像，没有真正的学生会话鉴权。
- `syncProgress` 只凭班级码、学号和课程 ID 即可读取或写入进度；“拒绝更少节点覆盖”只能防部分旧数据覆盖，不能替代身份认证。
- 论坛发帖、回复和点赞目前可以由客户端直接提交作者或学号，存在冒名、刷赞和不当内容风险。
- 公共排行榜需要继续做字段最小化，避免把学号等稳定标识当公开展示字段。
- 管理员身份不应长期绑定在前后端可推断的固定班级码和学号上；令牌需要过期、轮换、撤销和审计能力。

安全改造顺序应是：**先堵住公开读取 → 再给学生操作统一加会话鉴权 → 再迁移密码 → 最后补限流、日志、撤销和内容治理。** 每一步都要兼容现有账号和进度。

## 1. 永远分清证据层级

| 状态 | 至少需要什么证据 | 不能证明什么 |
|---|---|---|
| 本地完成 | 源码存在、目标差异清楚 | 构建成功、线上可用 |
| 本地验证通过 | 定向检查、构建、真实页面路径和目标尺寸通过 | 已部署、真实学生能用 |
| 已部署 | 云函数或静态资源部署命令成功，版本可识别 | 用户已经访问 |
| 已发布/线上可访问 | 生产地址无缓存地读到新版本，关键路径可走通 | 有真实使用、学习有效 |
| 真实学生使用 | 可识别的真实学生完成关键行为 | 学会了、愿意继续用 |
| 教师验收 | 教师实际按课堂目标审阅并确认 | 学生成绩提高 |
| 学习效果 | 无提示迁移题、前后测或持续表现有证据 | 因果一定来自产品 |
| 商业验证 | 主动咨询、明确付费意向、真实付款分别记录 | 可规模化盈利 |

必须长期避免的替代关系：

- HTTP 200、CloudBase 请求量、账号数不能替代 PV/UV、完成率或转化率；
- 页面漂亮、组件能打开、审计脚本通过不能替代教师验收；
- 导学分数、80 分门槛不能直接叫“掌握”；
- 留言、点赞、口头兴趣不能叫“付费意向”或“真实付款”；
- 本地补丁、线上 bundle 文本、部署日志三者互不替代。

## 2. 学生数据是第一红线

### 身份与进度

- `${classCode}:${studentId}` 是现有学生身份兼容锚点，不能随意修改。
- 当前课程化进度还包含课程 ID 扩展键；修改时必须兼容旧键、旧设备和已有云端记录。
- 注册会消耗邀请码名额，登录不会；永远不要混淆 `register` 和 `login`。
- 修改 `PlayerState` 时必须同时检查类型、默认值、`migrateState()`、`DATA_VERSION`、本地存储和云端同步。
- “完成节点更多就保留哪份”只是简化合并策略。若两个设备各完成了不同节点，只比较数量仍可能丢信息；后续应考虑集合级合并、更新时间或服务端版本控制。
- 任何迁移先做可回退方案和样本账号验证，再扩大到全体学生。

### 最小权限与最小暴露

- 密码、PIN、令牌、哈希、内部文档 ID 不进入公开响应，不写入前端日志和截图。
- 教师看板只返回教学决策需要的字段，不因“后台要方便”就返回整个数据库文档。
- 排行榜、论坛、学习报告默认使用昵称；学号、真名、班级信息只在明确授权的教师场景出现。
- 涉及未成年人数据时，还要明确保存周期、删除方式、反馈内容审核和家长/学校授权边界。

## 3. 互动不等于教学，做完题也不等于学会

每个知识点真正需要的是学习闭环，而不是一个看起来热闹的组件：

> 前测暴露误区 → 学生先判断/操作 → 观察或给出理由 → 分层提示 → 延迟揭示 → 变式练习 → 无帮助迁移题 → 错题回炉 → 教师看到错因和进步

重点注意：

- 首屏优先给学生一个能判断、能预测或能操作的问题，不要先放答案型知识卡。
- 探究类交互必须先预测、再观察、再解释，不能在标题、按钮、图片说明或可读 DOM 中提前泄露结论。
- “视觉上隐藏”不够；读屏文本、DOM、无障碍名称、预加载文案也不能剧透。
- 不同知识点的主要认知活动不同。判据辨析、性质证据、实验探究、操作决策、微观模型、规则推导、定量图表不能批量套同一模板。
- 互动要服务真实试卷迁移：学生最后要能解释依据、识别错因、处理边界情况并完成新情境题。
- 错题本不能只收题；要能保留错因、重做结果和下一次迁移表现。
- `audit:learning` 通过只说明结构规则通过，不能证明学生学会。

当前战略仍应深耕上海初中化学。高中内容作为储备，不应在真实学生验证不足时分散主线精力。

## 4. 科学准确性必须高于界面效果

这个项目面对学生，错误或过度简化会被反复学习，因此必须守住以下边界：

- 严格区分“操作—现象—证据—解释—结论”；看见现象不等于已经证明唯一原因。
- 结论写清适用条件。例如燃烧强弱、活泼性、收集方法、爆炸范围都不能脱离温度、浓度、材料形态和装置条件绝对化。
- 未检出某物质不能推出它一定不存在；检出水和二氧化碳也不能单独证明蜡烛只有某一种固定组成。
- 微观图示要守恒、粒子种类正确、系数与下标含义清楚；示意颜色和粒子大小要明确说明不是实物颜色和比例。
- 真实仪器图片用于“认得出”，动态图用于“看过程”；集气瓶、燃烧匙、量筒、液面和刻度等不能画出错误操作。
- 超纲机理放入可展开知识卡，并明确“本阶段不要求掌握”，不要压在主线步骤里。
- 一旦教师指出科学口径问题，要全局搜索组件、题目、知识卡、解析和素材说明，避免只改一个页面留下互相矛盾的旧文案。

## 5. 移动端真实路径比组件预览重要

最低体验验证应同时覆盖 `390×844` 手机和常用桌面尺寸，并从学生真实入口进入，而不是只打开孤立组件。

每次重点检查：

- 手机首屏是否能看懂下一步，叙事是否过长；
- 按钮、题干、解析、刻度、液面、装置图和实时数据是否互相遮挡；
- 是否有横向溢出、底部导航遮挡、弹窗无法关闭或滚动位置错误；
- 作答前是否剧透，作答后解释是否可见；
- 返回、重开、重做、错题本、迁移题和声音是否仍正常；
- 加载失败、图片缺失、控制台错误和旧 hydration 警告是否来自当前冷启动。

浏览器自动化的经验：

- 本地端口可能被占用，必须以开发服务实际输出为准，不能默认永远是 5173；
- 每次交互后重新读取当前页面结构，旧 selector 和旧 DOM 很容易造成误判；
- 页面打开成功不等于关键路径走通，必须实际完成一次学生流程。

## 6. 脏工作区和多工作树是长期工程风险

项目长期积累了大量 staged、unstaged 和未跟踪文件。以后每次修改前必须：

1. 确认当前目录是不是 `/Users/xudingkun/Projects/chem-challenge-tree`，还是另一个 worktree；
2. 查看目标文件的 staged 与 unstaged 差异；
3. 区分自己的修改和已有用户修改；
4. 采用最小增量补丁，不覆盖无关功能；
5. 只验证和报告实际检查过的范围。

特别注意：

- 定向 ESLint 通过不能写成“全仓 lint 通过”；
- `git diff --check` 应优先检查目标补丁，不能因为历史材料尾随空格就擅自清理无关文件；
- 构建 exit 0 时，大 chunk warning 是非阻塞警告，但仍要记录为性能债务；
- 项目文档和实际代码已经出现漂移，例如云函数数量、教师看板状态、题目/节点数量和课程数据组装方式不能只看旧 README 或 STATUS；
- 在代码基线稳定后，应把长期未提交工作拆成可审阅的小提交，否则回滚、归因和部署核对会越来越困难。

## 7. 部署是一项独立工作，不是构建的自然结果

标准顺序：

1. 明确本次要部署前端、哪个云函数、是否涉及数据库结构；
2. 运行与改动范围相称的检查；
3. CloudBase 身份过期时先重新登录；
4. 新云函数同时检查 `cloudbaserc.json`、函数部署和 HTTP 入口；
5. 部署后使用生产地址走真实路径；
6. 绕过 CDN 缓存核对资源版本，必要时比较 bundle 名称或哈希；
7. 记录部署时间、目标环境、版本和回滚办法。

前后端协议、令牌或进度结构同时变化时，要设计兼容窗口，避免只部署一侧导致老页面或老账号失效。

## 8. 真实验证应围绕“学生下一步会不会”

最小真实学生验证不需要很大样本，但必须记录关键过程：

- 是否愿意开始；
- 第一个卡点在哪里；
- 用时、提示次数、重试次数和中途退出；
- 是否完成；
- 下一道无帮助迁移题是否答对，并能否说出理由；
- 第二天是否愿意继续；
- 教师是否因此更容易判断错因并决定下一步教学。

不要只问“好不好玩”。真正有价值的问题是：

> 学生原来错在哪里？系统是否让这个错误暴露出来？点拨后能否在新题中独立解决？老师是否更快看懂了他的错因？

## 9. 产品、传播和商业化要使用同一条真实漏斗

建议长期统一为：

> 到达 → 开始体验 → 完成 → 主动咨询/留资 → 明确付费意向 → 真实付款 → 持续使用 → 学习结果

每一层单独采集，不能互相换算。短视频播放量也不能直接写成网站访问或学生完成。

产品定位应继续围绕：

> 全量知识地图 → 初步诊断 → 薄弱点地图 → 优先补缺 → 点拨和变式 → 错题回炉 → 阶段复测 → 家长/教师报告

前 20 号元素等专项适合做低门槛入口，但不是完整商品。30 天产品最多承诺完成一轮个性化重点补缺，不能承诺一个月学完整个初中化学或必然提分。

题目与素材的合规边界：

- 真题用于商业展示时优先独立改写题干、数据、选项、图形和解析；
- 前台可写“真题题型·改编”和年份，内部保留来源台账；
- 删除学校名称不等于解决版权问题；不要批量上传整卷、扫描图、原版式和原解析；
- 素材要保留来源与授权记录；学生反馈、课堂照片和报告截图必须打码；
- 论坛面向未成年人时需要举报、审核、删除、敏感内容处理和冒名防护。

## 10. 下一阶段的优先顺序

在扩大功能、发布视频或引导真实学生前，按以下顺序推进：

1. **线上安全闭环**：先部署 `manageCodes`，完成匿名双 403 和教师令牌正向验证；
2. **统一学生会话鉴权**：保护资料更新、进度读写和社交操作，并设计密码哈希兼容迁移；
3. **选一个真实学习闭环样板**：用 3–5 名学生无提示完成，记录首个卡点和迁移表现；
4. **补最小漏斗埋点**：到达、开始、完成、咨询分别采集；
5. **再决定扩建**：只有安全、学习或漏斗证据指向明确瓶颈时，才增加新功能。

本阶段默认不做：为了显得“平台完整”继续堆排行榜、徽章、每日任务、小程序或大量同质互动。

- [ ] 是否在正确项目/工作树？

- [ ] 是否影响身份键、数据结构、迁移或云端同步？
- [ ] 是否做了定向检查、构建和真实学生路径验证？
- [ ] 是否检查了手机尺寸、作答前 DOM 和控制台？

### 如果部署了

- [ ] 是否明确记录部署目标和时间？
- [ ] 是否在生产地址绕过缓存验证新版本？
- [ ] 云函数匿名反向测试和有效令牌正向测试是否都通过？
- [ ] 是否有兼容旧页面、旧账号和旧进度的方案？

### 如果要报告成果

- [ ] 本地、部署、发布、真实使用、教师验收、学习效果是否分开？
- [ ] 缺失数据是否写“尚未采集”？
- [ ] 是否避免用账号、请求量、播放量或留言替代转化和学习？
- [ ] 是否只使用真实、可复核、已打码的证据？

### 如果要继续做新功能

- [ ] 它解决的是学生真实卡点，还是只是让页面看起来更丰富？
- [ ] 它能否改善下一题迁移、教师判断或最小漏斗？
- [ ] 如果不能，先不做。
